ТЗ: Система сравнения товаров с локальной мультимодальной ИИ‑прослойкой
(браузерное расширение + бэкенд с Gemma 4/Hermes + сайт‑витрина)

1. Цели и сценарий использования
Пользователь устанавливает браузерное расширение (Chrome MV3).

Открывает страницу товара (AliExpress и др.), расширение “считывает” карточку товара, чистит DOM и отправляет данные на бэкенд.

Бэкенд ставит задачу в очередь, локальная мультимодальная модель Gemma 4 (через Hermes‑агент) нормализует данные: бренд, модель, цена, спецификации.

Нормализованные товары складываются в PostgreSQL, индексируются в Meilisearch и связываются между магазинами.

Сайт (Next.js) через GraphQL показывает объединённые карточки: один логический товар (например, iPhone 16 Pro) + массив цен/офферов из разных магазинов.

Расширение может также запрашивать с бэкенда “глобальную цену” и показывать пользователю, где дешевле.

2. Браузерное расширение (Vite + React + Tailwind + MV3)
2.1. Архитектура расширения
Manifest V3:

background — service worker.

content_scripts — для товарных доменов (AliExpress, и т.п.).

permissions: storage, activeTab, scripting, tabs.

host_permissions: домены магазинов и домен API бэкенда.

content_security_policy: разрешить connect-src к домену API (например, https://api.yoursite.com).

Стек:

Vite для сборки.

React + Tailwind для UI попапа/оверлея.

TypeScript для типизации и единых DTO с бэкендом.

2.2. Content Script: очистка и извлечение контекста
Задача: минимизировать объём “грязного” контента, чтобы не перегружать ИИ и VRAM.

Требования:

DOM‑фильтр (приоритетно, можно плюс RegExp):

удалить узлы: <script>, <style>, <svg>, <footer>, <nav>, <header>, <aside>, рекламные блоки;

удалить элементы по классам/ID: header, footer, nav, menu, sidebar, глобальная навигация и подвал.

Извлечение полезных блоков:

название товара (селекторы типа h1.product-title, #productTitle, и аналогичные на популярных площадках);

блок цены (значение + валюта);

таблица/список характеристик (specs, описание, технические детали);

URL текущей страницы;

идентификаторы товара, если доступны (SKU, ASIN, внутренние ID магазина).

Формат данных от content script к background:

ts
interface RawProductPayload {
  url: string;
  shop: string;            // "dns", "ozon", "aliexpress", ...
  title: string;
  priceBlockText: string;  // сырой текст с ценой/валютой
  specsText: string;       // очищенный текст характеристик / описание
  rawDomSnapshot?: string; // по необходимости: фрагмент HTML после фильтрации
}
2.3. Service Worker (background)
Задача: безопасно и централизованно отправлять данные на бэкенд.

Требования:

Получать RawProductPayload от content script через chrome.runtime.sendMessage или порт.

Извлекать JWT токен авторизации пользователя из chrome.storage.local.

Формировать REST‑запрос на бэкенд:

text
POST https://api.yoursite.com/products/ingest
Authorization: Bearer <JWT>
Content-Type: application/json
Body: RawProductPayload
Обрабатывать ошибки (нет токена, нет соединения, CORS‑ошибки) и уведомлять UI расширения.

2.4. UI расширения
Popup/overlay (React + Tailwind):

вход/регистрация пользователя (OAuth/JWT, связка с сайтом).

отображение статуса: “товар отправлен на анализ”, “найдено X предложений”, “дешевле на Y% в таком‑то магазине”.

Минимальный глобальный стейт (React state или Redux/Zustand по желанию) — хранить текущий анализируемый товар и результаты краткого запроса к API.

3. Бэкенд (NestJS + TypeScript): конвейер данных и ИИ
3.1. Общая архитектура
NestJS‑монолит (модульный):

Модуль auth (OAuth 2.0 / JWT).

Модуль products (REST, GraphQL, DTO, PostgreSQL).

Модуль queue (BullMQ + Redis).

Модуль ai (Hermes + Gemma 4).

Модуль search (Meilisearch).

Документация API: Swagger для REST, схема GraphQL для фронта.

CORS: настроить так, чтобы расширение (происходящее с доменов магазинов) и сайт (с вашего собственного домена) могли отправлять запросы.

3.2. REST API для расширения
Контроллер, например ProductsIngestController:

Эндпоинт: POST


/products/ingest.

Аутентификация: JWT (полученный через сайт/расширение).

DTO для входящих данных (соответствует RawProductPayload).

Логика:

валидировать DTO;

складывать задачу в очередь BullMQ.

3.3. Очереди (BullMQ + Redis) и управление VRAM
Задача: защитить RTX 4070 Ti (12 ГБ VRAM) от перегрузки.

Требования:

Очередь productProcessingQueue (Redis).

Воркер очереди с concurrency: 1 — строго один товар обрабатывается ИИ в единицу времени.

Возможность задания приоритетов (например, товары от активного пользователя обрабатывать раньше массовых задач).

Логирование и мониторинг состояния очереди (успехи/ошибки).

3.4. ИИ‑сервис (Hermes + Gemma 4, локальный Ollama/LM Studio)
Задача: превратить “грязный” текст/DOM карточки товара в стандартизированный JSON‑техпаспорт.

Требования:

Hermes‑агент формирует системный промпт:

роль: “товарный специалист”;

задача: извлечь строго { brand, model, price, currency, specs } без лишнего текста.

HTTP‑запрос к локальной инстанции Gemma 4 через Ollama/LM Studio (мультимодальная версия, если будут изображения).

Формат ответа: строго JSON:

json
{
  "brand": "Apple",
  "model": "iPhone 16 Pro",
  "price": 1299.99,
  "currency": "USD",
  "specs": {
    "storage": "256GB",
    "color": "Graphite",
    "screen_size": "6.3\"",
    "extra": "5G"
  }
}
Парсер и защита:

отказ от “сырого” текста — только парсим JSON;

если модель вернула невалидный формат, задача либо переотправляется, либо логируется как ошибка.

3.5. Валидация и сохранение (DTO + PostgreSQL + UUID)
DTO (class‑validator) для выходного JSON:

ts
class AiProductDto {
  @IsString() brand: string;
  @IsString() model: string;
  [club149076565|) price: number;
  @IsString(] currency: string;
  @IsObject() specs: Record<string, any>;
}
Генерация UUID (например, uuidv4) для сущности Product.

Модели PostgreSQL:

Таблица products (UUID PK, brand, model, specs, и метаданные).

Таблица prices (UUID PK, FK на products.id, магазин, цена, валюта, исходный URL, временная метка).

Миграции: через TypeORM/Prisma или другой ORM, с автоматизацией изменений схемы.

3.6. Умный матчинг товаров (Meilisearch)
Задача: склеить одинаковые товары из разных магазинов в одну логическую карточку.

Требования:

Индекс products_index в Meilisearch:

ключи: brand_normalized, model_normalized, возможно specs_keywords.

После сохранения нового товара:

нормализовать brand/model (lowercase, убрать мусор/вариации);

поискать похожий товар в индексе;

если найден матч — привязать новый price к существующему product;

если нет — создать новый product и индексировать.

3.7. Интерфейсы связи
REST API:

POST /products/ingest — от расширения.

дополнительные эндпоинты при необходимости (статус обработки, быстрый поиск).

GraphQL API:

основной интерфейс для сайта.

Пример схемы:

graphql
type Offer {
  shop: String!
  price: Float!
  currency: String!
  url: String!
}

type Product {
  id: ID!
  brand: String!
  model: String!
  specs: JSON!
  offers: [Offer!]!
}

type Query {
  product(id: ID!): Product
  products(search: String!): [Product!]!
}
4. Сайт / Личный кабинет (Next.js + Redux Toolkit + Tailwind)
4.1. Общая роль сайта
Личный кабинет пользователя: регистрация, логин, управление подписками, настройками.

Витрина сравнения товаров: просмотр объединённых карточек: один товар → массив цен из разных магазинов.

4.2. Технологический стек
Next.js (React + TypeScript).

Redux Toolkit для глобального состояния (фильтры, текущие товары, пользовательские настройки).

Tailwind CSS для быстрой адаптивной верстки.

4.3. Витрина сравнения
Требования:

Графический компонент “карточка товара”:

отображает brand, model, ключевые specs;

ниже — список офферов (магазин, цена, валюта, кнопка “перейти”).

Страница продукта:

загружает через GraphQL данные product(id);

хранит результат в Redux (для повторного использования и сравнения).

Страница поиска:

поле поиска (по model/brand);

список продуктов с краткой информацией;

переход на страницу товара по клику.

4.4. Глобальный стейт


(Redux Toolkit)
Slice для user (JWT, профиль).

Slice для products:

список текущих результатов поиска;

выбранный продукт и его офферы.

Slice для ui (фильтры, сортировка по цене, магазину, валюте).

5. Безопасность, инфраструктура и масштабирование
5.1. Безопасность
JWT‑аутентификация для сайта и расширения.

CORS:

разрешить запросы от домена сайта и из контекстов расширения.

SSL (HTTPS) для публичного API.

CSP в manifest расширения для ограничения сетевых запросов.

5.2. Инфраструктура
Контейнеризация (Docker) для NestJS, Redis, PostgreSQL, Meilisearch, сайта.

CI/CD — автоматическая сборка и деплой.

Мониторинг: логирование (например, ELK), метрики (Prometheus/Grafana).

6. ИИ‑дообучение (Gemma 4 12B + DoRA/LoRA) под товарку
6.1. Датасеты
Внешние:

LGS (Let's Go Shopping) — 15M image–caption e‑commerce пар.

Asos e‑commerce dataset — ~30k товаров с описаниями и характеристиками.

Авто‑датасеты (car-images) для обучения домена автомобилей.

Собственные:

реальные фотки/картинки товаров (ламинат, болты, мебель и т.п.) + техпаспорт в целевом JSON.

6.2. Формат обучающего файла
Единый train.jsonl, каждое наблюдение — пример:

Вариант instruction‑style:

json
{"instruction": "Определи товар по изображению/карточке и верни техпаспорт в JSON.", "input": "<image_or_text>", "output": "{\"brand\":\"Apple\",\"model\":\"iPhone 16 Pro\",...}"}
Вариант chat‑style:

json
{
  "messages": [
    {"role":"system","content":"Ты ассистент по товарной классификации. Всегда возвращаешь чистый JSON техпаспорта."},
    {"role":"user","content":"<image:img_000001.jpg>\n<dom_text>..."},
    {"role":"assistant","content":"{\"brand\":\"Apple\",\"model\":\"iPhone 16 Pro\", ... }"}
  ]
}
Общая схема JSON (техпаспорт) должна совпадать с тем, что ожидает NestJS DTO.

6.3. Объём данных
Для стартового прототипа: 5–10 тыс. хорошо размеченных примеров.

Для устойчивой товарной модели: 30–100 тыс. примеров, в том числе собственных и “грязных” реальных кейсов.

Если хочешь, следующим шагом могу:

расписать конкретные SQL‑схемы таблиц products и prices с полями;

или выдать черновик manifest.json для расширения, где уже учтены CSP, разрешения и базовая конфигурация.
